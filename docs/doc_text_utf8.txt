Database Setup 📘 Guidance: Always separate the database superuser from the application user. The application user needs only SELECT, INSERT, UPDATE, DELETE on its own tables — never CREATE, DROP, or superuser privileges. 3.1 Create Database User and Database sudo -u [postgres | db-superuser] [psql | mysql | sqlplus] -- Create a dedicated application user CREATE USER [db-app-user] WITH PASSWORD '[STRONG_RANDOM_PASSWORD]'; -- Create the application database CREATE DATABASE [db-name] OWNER [db-app-user]; -- Grant privileges GRANT ALL PRIVILEGES ON DATABASE [db-name] TO [db-app-user]; -- Verify \l [db-name] \q ⚠ Password security Use a strong random password (minimum 24 characters, mixed alphanumeric and symbols). Store it in a password manager — it is required in §8 Environment Variables. Never commit it to version control. 3.2 Run the Schema Migration 📘 Guidance: Option A (automatic): Flyway / Liquibase runs on first application startup — no manual step needed. Option B (manual): run the SQL files directly in the correct version order. # Option A: Automatic on startup (Flyway / Liquibase) # Migration runs when the application first starts. Verify in §9.1 logs. # Option B: Manual SQL migration [db-cli] -h [host] -U [db-app-user] -d [db-name] -f /path/to/V1__init_schema.sql ⚠ Migration tool warning Do NOT run SQL migration files manually AND let the tool run automatically. Choose one approach. Running both causes checksum conflicts or duplicate-table errors. 3.3 Configure Database Authentication sudo nano /etc/postgresql/16/main/pg_hba.conf # Ensure this line exists: # TYPE DATABASE USER ADDRESS METHOD host [db-name] [db-app-user] 127.0.0.1/32 md5 sudo systemctl reload [database-service] 3.4 Test the Database Connection [db-cli] -h 127.0.0.1 -U [db-app-user] -d [db-name] -c "SELECT NOW();" # Expected: a row showing the current timestamp 4. Reverse Proxy Configuration 📘 Guidance: 1. Redirect HTTP (port 80) → HTTPS (port 443) 2. Proxy HTTPS → application port on localhost 3. Block direct access to sensitive directories (uploads, logs, etc.) 5.1 Obtain a TLS Certificate Option A — Let's Encrypt (internet-facing deployments) sudo apt install -y certbot python3-certbot-[nginx | apache] sudo certbot --[nginx | apache] -d [your-domain.com] # Verify auto-renewal timer sudo systemctl status certbot.timer Option B — Customer-provided certificate (intranet) sudo mkdir -p /etc/[reverse-proxy]/ssl/[project-name] sudo cp [fullchain.pem] /etc/[reverse-proxy]/ssl/[project-name]/fullchain.pem sudo cp [privkey.pem] /etc/[reverse-proxy]/ssl/[project-name]/privkey.pem sudo chmod 600 /etc/[reverse-proxy]/ssl/[project-name]/privkey.pem 5.2 Create the Virtual Host Configuration sudo nano /etc/nginx/sites-available/[project-name] # Redirect HTTP → HTTPS server { listen 80; server_name [your-domain.com]; return 301 https://$host$request_uri; } # Main HTTPS server block server { listen 443 ssl; server_name [your-domain.com]; ssl_certificate [/path/to/fullchain.pem]; ssl_certificate_key [/path/to/privkey.pem]; ssl_protocols TLSv1.2 TLSv1.3; ssl_ciphers HIGH:!aNULL:!MD5; add_header Strict-Transport-Security "max-age=31536000" always; add_header X-Frame-Options DENY always; add_header X-Content-Type-Options nosniff always; # Must be larger than the app file size limit client_max_body_size [10M]; # BLOCK direct access to sensitive directories location /[uploads-dir]/ { deny all; return 403; } # Proxy all requests to the application location / { proxy_pass http://127.0.0.1:[app-port]; proxy_http_version 1.1; proxy_set_header Host $host; proxy_set_header X-Real-IP $remote_addr; proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; proxy_set_header X-Forwarded-Proto $scheme; proxy_connect_timeout [60s]; proxy_read_timeout [60s]; } access_log /var/log/nginx/[project-name]-access.log; error_log /var/log/nginx/[project-name]-error.log; } ⚠ client_max_body_size Must be greater than the application's file size limit. Otherwise Nginx rejects the upload before it reaches the application and users see a cryptic 413 error. 5.3 Enable the Site sudo ln -s /etc/nginx/sites-available/[project-name] \ /etc/nginx/sites-enabled/[project-name] sudo rm -f /etc/nginx/sites-enabled/default # remove if it conflicts sudo nginx -t # must pass before reloading # Expected: nginx: configuration file ... test is successful sudo systemctl reload nginx 6. Backup &amp; Recovery 📘 Guidance: Include a timestamp in every backup filename. Use 'find ... -mtime +N -delete' in the cron job to automatically remove backups older than N days. Adjust N to match storage capacity. 11.1 Database Backup Automated (daily cron) sudo crontab -u [postgres] -e # Add (runs at 02:00 nightly, retains 30 days): 0 2 * * * [pg_dump --format=custom --compress=9] \ --file=/opt/[project-name]/backups/db/[project-name]_$(date +\%Y\%m\%d).[pgdump|sql] \ [db-name] &amp;&amp; \ find /opt/[project-name]/backups/db -name '*.[pgdump|sql]' -mtime +30 -delete 11.2 File Upload Backup (if applicable) sudo tar -czf /opt/[project-name]/backups/uploads_$(date +%Y%m%d).tar.gz \ -C /opt/[project-name] uploads/ # Automate: add to cron alongside database backup # find /opt/[project-name]/backups -name 'uploads_*.tar.gz' -mtime +30 -delete Manual (ad-hoc) sudo mkdir -p /opt/[project-name]/backups/db sudo chown [postgres]:[postgres] /opt/[project-name]/backups/db sudo -u [postgres] [pg_dump | mysqldump] \ [--format=custom --compress=9] \ --file=/opt/[project-name]/backups/db/[project-name]_$(date +%Y%m%d_%H%M%S).[pgdump|sql] \ [db-name] 11.3 Restore from Backup Restore database sudo systemctl stop [project-name] sudo -u [postgres] psql -c "DROP DATABASE [db-name];" sudo -u [postgres] psql -c "CREATE DATABASE [db-name] OWNER [db-app-user];" sudo -u [postgres] [pg_restore | psql] \ [--dbname=[db-name] --verbose] \ /opt/[project-name]/backups/db/[project-name]_YYYYMMDD.[pgdump|sql] sudo systemctl start [project-name] Restore file uploads sudo systemctl stop [project-name] sudo tar -xzf /opt/[project-name]/backups/uploads_YYYYMMDD.tar.gz -C /opt/[project-name] sudo chown -R [app-user]:[app-user] /opt/[project-name]/uploads sudo systemctl start [project-name] ⚠ Migration tool warning Rolling back a JAR does NOT undo applied database migrations. If the old version cannot start against the newer schema, a full database restore is required. Always test schema changes in a staging environment before production. 12.
