Conventions & Notation
Entity State Machines
Critical: Every status used in the use cases is defined below. Terminal states do not permit normal outbound transitions; retained records remain available for history.
User Account status workflow
ACTIVE -> LOCKED (System after five consecutive failed sign-ins, UC61; or System Administrator, UC56).
LOCKED -> ACTIVE (System after the 15-minute lock period, UC61; or System Administrator, UC56).
ACTIVE or LOCKED -> INACTIVE (System Administrator, UC54).
INACTIVE -> ACTIVE (System Administrator, UC54, after validation).
No terminal state; account history is retained.
Product status workflow
ACTIVE -> INACTIVE (Warehouse Manager or System Administrator, UC08: Discontinue Product).
INACTIVE -> ACTIVE (Warehouse Manager or System Administrator, UC06, after reactivation validation).
No terminal state; historical transactions remain available.
Supplier status workflow
ACTIVE -> INACTIVE (Purchasing Staff, Warehouse Manager, or System Administrator, UC14: Deactivate Supplier).
INACTIVE -> ACTIVE (authorized actor, UC12, after reactivation validation).
No terminal state; historical purchase and inbound references remain available.
Storage Location status workflow
AVAILABLE <-> OCCUPIED (System when posted inventory changes between zero and positive quantity, UC23/UC31/UC36).
AVAILABLE or OCCUPIED -> BLOCKED (authorized warehouse control outside the 65-UC operational baseline).
BLOCKED -> AVAILABLE or OCCUPIED (authorized warehouse control after issue resolution).
AVAILABLE, OCCUPIED, or BLOCKED -> INACTIVE (administrative configuration outside this UCS baseline).
INACTIVE is terminal for new operational selection; history remains visible.
Product Lot status workflow
ACTIVE -> EXPIRED (System when expiry date passes).
ACTIVE -> DEPLETED (System when on-hand quantity becomes zero after UC31 or UC36).
ACTIVE or EXPIRED -> BLOCKED (authorized quality/warehouse decision outside the operational baseline).
EXPIRED and DEPLETED are terminal for normal reservation; BLOCKED may be released only by authorized control.
Purchase Order status workflow
A new Purchase Order is created in DRAFT status by Purchasing Staff (UC65).
DRAFT -> CONFIRMED (approved purchasing reference outside this operational UCS baseline).
CONFIRMED -> PARTIALLY_RECEIVED (System after a linked partial receipt, UC22).
CONFIRMED or PARTIALLY_RECEIVED -> RECEIVED (System after linked eligible quantities are fully received, UC22).
DRAFT or CONFIRMED -> CANCELLED (authorized purchasing process outside this UCS baseline).
RECEIVED and CANCELLED are terminal.
Sales Order status workflow
A new Sales Order is created in DRAFT status by Sales Staff (UC64).
DRAFT -> CONFIRMED (authorized sales process after availability check in UC30).
CONFIRMED -> PARTIALLY_ISSUED (System after a permitted partial issue, UC31).
CONFIRMED or PARTIALLY_ISSUED -> ISSUED (System after all eligible quantity is issued, UC31).
DRAFT or CONFIRMED -> CANCELLED (authorized sales process; linked outbound cancellation uses UC29).
ISSUED and CANCELLED are terminal.
Inbound Order status workflow
DRAFT -> READY (Purchasing Staff, UC18 or UC19: submit complete order).
READY -> RECEIVING (Warehouse Staff, UC22: start receipt).
RECEIVING -> RECEIVED (Warehouse Staff, UC22: complete receipt decisions).
RECEIVED -> PUTAWAY_COMPLETED (Warehouse Staff, UC23: complete destination allocations).
DRAFT or READY -> CANCELLED (Purchasing Staff, UC21).
PUTAWAY_COMPLETED and CANCELLED are terminal.
Outbound Order status workflow
DRAFT -> RESERVED (Sales Staff, UC30: create valid reservation).
DRAFT or RESERVED -> READY (Sales Staff, UC26: create/submit operational outbound order).
READY -> ISSUING (Warehouse Staff, UC31: start issue).
ISSUING -> ISSUED (Warehouse Staff, UC31: complete issue).
DRAFT, RESERVED, or READY -> CANCELLED (Sales Staff, UC29).
ISSUED and CANCELLED are terminal.
Inventory Reservation status workflow
ACTIVE -> CONSUMED (System after confirmed issue, UC31).
ACTIVE -> RELEASED (System after eligible outbound cancellation or quantity reduction, UC29/UC27).
ACTIVE -> EXPIRED (System when the configured reservation expiry time passes).
CONSUMED, RELEASED, and EXPIRED are terminal.
Stocktake Session status workflow
PLANNED -> IN_PROGRESS (Warehouse Staff begins the first assigned bin, UC34).
IN_PROGRESS -> COUNTED (System when every selected bin is COMPLETED, UC35).
COUNTED -> APPROVED (Warehouse Manager approves all discrepancies, UC36).
APPROVED -> COMPLETED (System after atomic adjustment posting, UC36).
PLANNED -> CANCELLED (authorized scheduling control outside this UCS baseline).
COMPLETED and CANCELLED are terminal.
Stocktake Location status workflow
PENDING -> IN_PROGRESS (Warehouse Staff, UC34: start bin count).
IN_PROGRESS -> COMPLETED (Warehouse Staff, UC34: submit complete bin count).
COMPLETED -> RECOUNT_REQUIRED (Warehouse Manager, UC36).
RECOUNT_REQUIRED -> IN_PROGRESS -> COMPLETED (Warehouse Staff, UC34).
COMPLETED is terminal only after the parent session reaches COMPLETED.
Notification status workflow
UNREAD -> READ (recipient opens the notification, UC50).
UNREAD or READ -> EXPIRED (System after the configured retention or action period).
EXPIRED is terminal.

UC Types at a Glance
UC01: View Warehouse Information
Goal: Allows the user to view information about the single warehouse configured in the system.
Main Flow
[U] The user opens Warehouse Overview.
[S] The system identifies the single warehouse configured for this release.
[S] The system verifies that the warehouse record is visible to the user's role.
[S] The system displays warehouse code, name, address, contact information, and operational status.
[S] The system displays summary counts for active, occupied, available, blocked, and inactive storage locations.
[U] The user reviews the information and may open UC02 View Storage Location Map.
Alternative Flows
AF-01 - Warehouse configuration missing: No warehouse record is configured. The system displays a configuration-required notice and does not infer or create a warehouse automatically.
AF-02 - Warehouse inactive: The configured warehouse is INACTIVE. The system displays the record in read-only mode with an operational warning.
Business Rules
BR-01: Exactly one active Warehouse is permitted in this release (see PRD DR-01).
BR-02: Warehouse information is read-only in this use case.
BR-03: Location summary counts must be calculated from locations belonging to the configured warehouse.
Request Fields - WarehouseOverviewRequest
On success: Warehouse Overview displays the configured warehouse and accurate location-status summary.
Allowed Roles
System Administrator, Warehouse Manager, Warehouse Staff
Verification Criteria
Additional scenarios to cover in tests:
View an ACTIVE warehouse.
View an INACTIVE warehouse.
Verify location counts match the location map.
Attempt access with a role that is not allowed.

UC02: View Storage Location Map
Goal: Allows the user to view the predefined areas, racks, and storage bins in the warehouse.
Main Flow
[U] The user opens Storage Location Map.
[S] The system loads the first page of storage location records allowed for the user's role.
[U] The user enters or changes one or more search and filter values.
[S] The system validates the filter values and applies the authorized data scope.
[S] The system displays the warehouse-area-rack-bin hierarchy, location code, floor area, status, distance rank, and current product count, the matching-record count, and pagination controls.
[U] The user may change sorting, move between pages, clear filters, or open an available record/action.
Alternative Flows
AF-01 - No matching records: At the result step, no record satisfies the active filters. The system displays an explicit no-results state and keeps the filters available for revision.
AF-02 - Invalid filter combination: When a date range or numeric range is invalid, the system does not run the search and identifies the fields that must be corrected.
AF-03 - Location structure not configured: The warehouse has no storage locations. The map displays a configuration-required empty state.
Business Rules
BR-01: Only storage location records within the signed-in user's authorized scope may be returned (see PRD GB-02).
BR-02: Results are sorted by area, rack, and bin code ascending unless the user selects another supported sort.
BR-03: Pagination must return a stable result order and a total matching-record count.
BR-04: Every displayed location must belong to the single configured warehouse (see PRD DR-01 and DR-02).
BR-05: A location code is unique within the warehouse.
Request Fields - StorageLocationListFilter
On success: Storage Location Map displays the matching records and active filter summary.
Allowed Roles
System Administrator, Warehouse Manager, Warehouse Staff
Verification Criteria
Additional scenarios to cover in tests:
Open the list with default filters.
Search using a complete identifier.
Combine two or more filters.
Use a filter that returns no results.
Change page size and verify stable pagination.

UC03: Locate Product
Goal: Allows the user to find the current storage location and available quantity of a product.
Main Flow
[U] The user opens Product Location Lookup and searches by product code, name, or barcode.
[S] The system validates the search and resolves the matching product.
[U] The user optionally narrows the result by lot, area, location status, or available-only filter.
[S] The system reads the current derived Inventory balance by Product + StorageLocation + ProductLot.
[S] The system displays each matching bin with lot, expiry date, on-hand, reserved, and available quantity.
[U] The user may open the selected product detail or movement history.
Alternative Flows
AF-01 - Product not found: No active or historical product matches the search. The system displays a no-results state and does not infer a location.
AF-02 - Product exists with zero stock: The product exists but has no positive balance. The system shows zero available quantity and the fixed default location, when configured, as reference only.
AF-03 - Inventory record changed during lookup: A balance changes after the result loads. The result retains its displayed update time until the user refreshes.
Business Rules
BR-01: Inventory is displayed by Product + StorageLocation + ProductLot; InventoryTransaction remains the movement source of truth (see PRD DR-14).
BR-02: Available quantity equals on-hand quantity minus active reserved quantity and may not be negative (see PRD DR-10 and DR-11).
BR-03: Only bins within the configured warehouse and the user's authorized scope are displayed.
Request Fields - ProductLocationLookupRequest
On success: The current location and quantity rows are displayed with their last-update time.
Allowed Roles
System Administrator, Warehouse Manager, Warehouse Staff, Sales Staff
Verification Criteria
Additional scenarios to cover in tests:
Locate a product by product code.
Locate a product by barcode.
Locate a product stored in multiple bins and lots.
Locate a product with zero available quantity.
Filter to available-only inventory.

UC05: Create Product
Goal: Allows the manager to create a product under a product group and enter the attributes configured for that group.
Main Flow
[U] The user opens Product Create and selects Create.
[S] The system displays a blank product form and the permitted reference values.
[U] The user enters the required and optional information and submits the form.
[S] The system validates field rules, uniqueness, references, and the user's permission.
[S] The system creates the product with status ACTIVE and records audit information.
[S] The system opens the created product and displays a success confirmation.
Alternative Flows
AF-01 - Required or invalid value: At validation, one or more required values are missing or invalid. The system keeps the form data and identifies every field that must be corrected.
AF-02 - Duplicate business identifier: The system finds a record that violates this uniqueness rule: Product code and barcode must be unique within BMWMS (see PRD DR-03 and GB-04). No duplicate is created and the conflicting field is identified.
AF-03 - Invalid reference: A selected reference is unavailable or ineligible. The system keeps the form open and explains that the selected product group, unit, default fixed location, and configured attributes must be active and compatible.
Business Rules
BR-01: Product code and barcode must be unique within BMWMS (see PRD DR-03 and GB-04).
BR-02: All required fields must pass business validation before the record is saved.
BR-03: A successful creation stores the product with status ACTIVE and records the creator and creation time.
BR-04: The creation action is written to the audit log (see PRD GB-20).
BR-05: the selected product group, unit, default fixed location, and configured attributes must be active and compatible.
BR-06: A product belongs to exactly one product group.
BR-07: The product group determines the displayed attributes and whether lot or expiry information is required (see PRD DR-04 and DR-05).
BR-08: Safety stock is configured per product and may be zero (see PRD GB-10).
Request Fields - ProductCreateRequest
On success: The new product detail is displayed with status ACTIVE.
Allowed Roles
System Administrator, Warehouse Manager
Verification Criteria
Additional scenarios to cover in tests:
Create a product with all valid required values.
Create a product with valid optional values.
Submit with a required field missing.
Submit a duplicate business identifier.
Cancel creation before saving.

UC06: Edit Product
Goal: Allows the manager to update permitted product information.
Main Flow
[U] The user opens an eligible product and selects Edit.
[S] The system opens Product Edit with the current values and edit restrictions.
[U] The user changes one or more permitted values and submits the form.
[S] The system rechecks the current record version, status, field rules, references, and uniqueness.
[S] The system saves the permitted changes and records the update in the audit log.
[S] The system returns to the product detail and confirms the update.
Alternative Flows
AF-01 - Record state no longer permits editing: At save time, the record is no longer in ACTIVE or INACTIVE. The system rejects the update, reloads the current record, and explains why it cannot be edited.
AF-02 - Concurrent update: Another user saved a newer version after the form was opened. The system does not overwrite it and asks the user to review the latest values.
AF-03 - Validation failure: One or more changed values fail validation. The system keeps all unsaved changes and identifies the invalid fields.
Business Rules
BR-01: The record is editable only in ACTIVE or INACTIVE.
BR-02: Product code is immutable after the product has any transaction history; barcode must remain unique.
BR-03: A successful update records the editor, update time, and before/after audit summary (see PRD GB-20).
BR-04: Changing product group is rejected when existing attribute, lot, or transaction data would become incompatible.
BR-05: Reactivating an INACTIVE product requires valid active master references.
Request Fields - ProductUpdateRequest
On success: The updated product detail is displayed with a success confirmation.
Allowed Roles
System Administrator, Warehouse Manager
Verification Criteria
Additional scenarios to cover in tests:
Update one permitted product field.
Update multiple permitted fields.
Attempt to change a protected identifier.
Attempt to update an ineligible state.
Simulate a concurrent update conflict.

UC07: View Product Details
Goal: Allows the user to view full product master data, group attributes, stock rules, and status.
Main Flow
[U] The user selects a product record from the related list or search result.
[S] The system verifies that the record exists and is visible to the user's role.
[S] The system opens Product Details.
[S] The system displays identity, group, unit, configured attribute values, lot/expiry rules, safety stock, fixed location, status, current balance summary, and last update.
[S] The system shows only the actions that are valid for the current status and role.
[U] The user reviews the information and may navigate to an available related view or action.
Alternative Flows
AF-01 - Record no longer available: After the user selects the record, the product no longer exists or is outside the user's scope. The system returns to the source view and displays a non-destructive notice.
AF-02 - Historical or inactive record: The record is inactive or completed. The system still displays retained history but hides actions that are not permitted in the current state.
Business Rules
BR-01: The selected product identifier must resolve to exactly one record.
BR-02: Displayed actions are determined by the signed-in user's fixed role and the record's current state (see PRD GB-02).
BR-03: Historical records remain viewable and are not physically deleted (see PRD GB-03).
BR-04: Dynamic attribute labels and values must reflect the product's assigned group configuration.
BR-05: Inventory summary values use the current derived balance and display the calculation time.
Request Fields - ProductDetailRequest
On success: Product Details displays the complete authorized view of the selected product.

UC08: Discontinue Product
Goal: Allows the manager to prevent a product from being used in new transactions while retaining its history.
Main Flow
[U] The user opens the eligible product and selects Discontinue.
[S] The system displays the confirmation, current status, and consequences of the action.
[U] The user enters the discontinuation reason, selects the intended action if applicable, and confirms.
[S] The system rechecks the current status, blocking dependencies, and the user's permission.
[S] The system changes the status to INACTIVE and records the reason and actor.
[S] The system refreshes the record and displays a success confirmation.
Alternative Flows
AF-01 - Ineligible current state: The record is not in ACTIVE. The system does not change its status and displays the currently allowed actions.
AF-02 - Blocking dependency: The system finds a blocking dependency. The action is rejected because the product must not have an uncompleted inbound line, outbound line, or active reservation; historical transactions do not block discontinuation.
AF-03 - User cancels confirmation: The user closes the confirmation without submitting. The record remains unchanged and no audit event is created for a completed action.
Business Rules
BR-01: The action may start only when the product is in ACTIVE.
BR-02: the product must not have an uncompleted inbound line, outbound line, or active reservation; historical transactions do not block discontinuation.
BR-03: The discontinuation reason is required and is retained in history.
BR-04: The record is not physically deleted; the status change preserves historical references (see PRD GB-03).
BR-05: The status change is written to the audit log (see PRD GB-20).
Request Fields - ProductDiscontinueRequest
On success: The product detail is displayed with status INACTIVE.
Allowed Roles
System Administrator, Warehouse Manager
Verification Criteria
Additional scenarios to cover in tests:
Complete discontinue from an eligible state.
Cancel from the confirmation dialog.
Attempt the action from an ineligible state.
Attempt the action while a blocking dependency exists.

UC09: Trace Product Movement History
Goal: Allows the user to review inbound, outbound, stocktake, reservation, and inventory adjustment history for a product.
Main Flow
[U] The user opens Product Movement History for the selected product.
[S] The system displays the latest authorized inbound, putaway, reservation, release, outbound, stocktake, and approved adjustment events.
[U] The user enters a date range or selects event, status, product, lot, or location filters when available.
[S] The system validates the filters and retrieves the retained history.
[S] The system displays event time, event type, signed quantity effect, lot, bin, source reference, actor, and resulting balance when available.
[U] The user may change sorting, clear filters, or open an available referenced record.
Alternative Flows
AF-01 - No history in the selected period: No event matches the filters. The system displays a no-history state without changing the selected record or filters.
AF-02 - Invalid date range: The start date is after the end date or exceeds the allowed reporting range. The system identifies the invalid range and does not run the query.
Business Rules
BR-01: History is read-only and is ordered newest first by default.
BR-02: Only posted or retained business events are shown; cancelled records remain visible for traceability.
BR-03: The displayed history must be reconcilable to immutable transaction or audit records where applicable (see PRD GB-12 and GB-20).
BR-04: InventoryTransaction rows are immutable; corrections are shown as compensating events (see PRD GB-12).
Request Fields - ProductHistoryFilter
On success: Product Movement History displays the matching retained history and active filters.
Allowed Roles
System Administrator, Warehouse Manager, Warehouse Staff, Purchasing Staff, Sales Staff

UC63: Reset Forgotten Password
Goal: Allows a registered user to request and complete password recovery.
Main Flow
[U] The user opens Forgot Password and enters the registered username or email.
[S] The system returns the same generic acknowledgement whether or not a matching account is found.
[S] For an eligible account, the system invalidates prior unused tokens and sends a single-use reset link or code to the registered email.
[U] The user opens the link or submits the code, then enters and confirms a new password.
[S] The system validates token identity, single-use state, 15-minute expiry, account eligibility, and password policy.
[S] The system replaces the credential, invalidates the token and active sessions according to policy, records the event, and directs the user to Sign In.
Alternative Flows
AF-01 - Unknown username or email: No eligible account matches. The system still displays the generic acknowledgement and sends no message.
AF-02 - Expired or already used token: The token is invalid. The system does not change the password and offers to start a new reset request.
AF-03 - New reset requested: A second request is issued. The system invalidates every earlier unused token and sends only the new token.
AF-04 - Password fails policy or confirmation: The token remains usable until expiry, but the credential is not changed. The system identifies the password-policy or mismatch issue.
AF-05 - Account inactive: The system keeps the public response generic and does not issue a usable reset token for an INACTIVE account.
Business Rules
BR-01: Public reset requests always return a generic acknowledgement to prevent account discovery.
BR-02: Reset links or codes are single-use and expire after 15 minutes; a new token invalidates prior unused tokens (see PRD GB-19).
BR-03: The new password must satisfy the same policy as UC60 and must not be a prohibited recent password.
BR-04: Plaintext passwords and reset token values are never written to logs.
BR-05: Successful and failed reset completion attempts are recorded in security audit history.
Request Fields - ForgottenPasswordResetRequest
On success: The password is reset, the token is invalidated, and the user is directed to Sign In with a generic success message.
Allowed Roles
System Administrator, Warehouse Manager, Warehouse Staff, Purchasing Staff, Sales Staff
